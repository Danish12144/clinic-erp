## Project state — read this first

This repo pivoted from a single-tenant demo scaffold to **Clinic ERP + CRM**, a multi-tenant SaaS product, being built module-by-module against a from-scratch design. The authoritative design docs are:

- `docs/PRD-ARCHITECTURE.md` — full product requirements + technical architecture (30 sections: roles, permission matrix, modules, workflows, entities, API structure, multi-tenant/auth/RBAC strategy, deployment, phasing, open questions).
- `docs/DATABASE-SCHEMA.md` + `docs/schema/clinic_erp_schema.sql` — the complete hand-designed Postgres schema (all modules), with a narrative doc explaining the design decisions and its own changelog of what's since been added during implementation.

**Everything else describing "the system" predates this pivot and is superseded — do not trust it as current behavior:**
- `README.md`, `docs/architecture.md`, `docs/database-schema.md`, `docs/api-spec.md` describe the original single-tenant demo's intended design.
- `backend-legacy-node-scaffold/` is the original Node/Express/TypeScript backend, preserved (renamed, not deleted) when the new Python/FastAPI backend replaced it in `backend/`. Nothing in it is wired to anything current.
- `frontend-legacy-demo/` is the original single-tenant React/Vite demo UI (a single `App.tsx` with hardcoded mock data) — preserved (renamed, not deleted) the same way `backend-legacy-node-scaffold/` was, when the new SaaS frontend scaffold took over the `frontend/` directory name. Nothing in it is wired to anything current.

**Build order is strict and incremental, one module at a time**, following `docs/PRD-ARCHITECTURE.md` §10's module list — each module gets Models, Schemas, Repository, Service, Router, and Tests (unit + integration + tenant-isolation) before the next one starts. Do not start a new module without being asked to.

## Architecture notes — things that aren't obvious from reading one file

**Migrations are hand-written raw SQL, not autogenerated**, and are a deliberate curated subset of `docs/schema/clinic_erp_schema.sql` — only what the modules built so far actually use (e.g. migration `0001` skips `doctor_profiles`/`staff_profiles`/`user_branch_assignments` even though they're in the master schema, because no module needs them yet). When adding a table for a new module, copy its DDL from the master schema file into a new migration rather than letting `alembic revision --autogenerate` invent something that might drift from the design doc. Keep both in sync — see `docs/DATABASE-SCHEMA.md`'s changelog note for the pattern (two tables, `otp_codes` and `user_sessions`, were discovered as needed *during* Auth implementation and added to the master schema doc after the fact — this is expected, not a process failure).

**Tenant isolation requires a non-superuser DB role — this is the single easiest thing to break.** `DATABASE_URL` (used by the running app) must point at `app_user` (created in migration `0002`), never at the `postgres` superuser used by `DATABASE_URL_SYNC` for migrations. Postgres superusers **always bypass Row-Level Security**, `FORCE ROW LEVEL SECURITY` notwithstanding — connecting the app as `postgres` silently defeats every tenant-isolation guarantee in the system with no error of any kind. This exact bug was caught by the `tests/tenant_isolation/` suite the first time the Auth module's tests ran (cross-tenant login and cross-tenant row reads both "worked" until the role was fixed) — if a future change to `app/core/db.py` or `.env` makes tenant isolation tests fail in a way that looks like RLS just isn't applying, check this first.

**`app/core/db.py` has two session context managers, not one**: `tenant_session(tenant_id)` for all normal authenticated request handling, and `platform_admin_session()` for the narrow, explicitly-justified cross-tenant bypass (currently used only to resolve a clinic slug to a tenant id pre-authentication, in `app/modules/auth/repository.py::TenantResolutionRepository`). Any new use of `platform_admin_session()` should be treated as a design decision worth a comment explaining why, not a convenience.

**RLS session variables use `set_config(..., true)`, not `SET LOCAL`.** `SET LOCAL x = :param` is not valid Postgres syntax with bind parameters (`SET` isn't a normal DML statement) — this broke on first real test run against a live DB (`syntax error at or near "$1"`). `SELECT set_config('app.current_tenant_id', :value, true)` is the parameterizable equivalent and is just as transaction-scoped.

**The async test suite uses `NullPool` when `ENVIRONMENT=test`** (`app/core/db.py`), not the default pooled engine. pytest-asyncio's function-scoped event loops don't mix with pooled asyncpg connections opened on a previous test's loop — surfaces on Windows as a confusing `AttributeError` / "Event loop is closed" during teardown. `tests/conftest.py` sets `ENVIRONMENT=test` by default; don't remove that without addressing the underlying loop-scoping issue differently.

**JWT access tokens carry the resolved permission set, not just a role.** `app/core/security.py::create_access_token` embeds the user's *effective* permissions (role defaults + `permission_overrides`, resolved once at login/refresh by `PermissionRepository.resolve_effective_permissions`) directly in the token payload. `app/api/deps.py::require_permission(...)` checks membership in that embedded list — zero DB hits on protected routes. A clinic owner revoking a permission takes effect for that user on their *next token refresh*, not instantly. This is what makes the "Owner turns on vitals-recording for Receptionists at their clinic" requirement (PRD §3/§13) work without per-request DB queries.

**Refresh tokens and OTP codes are opaque and stored only as SHA-256 hashes** (`user_sessions.refresh_token_hash`, `otp_codes.code_hash`) — never the raw value, so a DB read alone can't be used to impersonate a session or replay a login code. OTP delivery is a `ConsoleOtpSender` that just logs the code (`app/modules/auth/otp_sender.py`) — not production-safe, a placeholder until the Communications module ships a real WhatsApp/SMS adapter; `AuthService` also echoes the code back in the API response body whenever `ENVIRONMENT != production`, which is what lets integration tests complete the OTP flow with no external provider.

**`vitals`, `prescriptions`, and `audit_logs` are append-only at the database level**, not just by app convention — a `BEFORE UPDATE OR DELETE` trigger (`prevent_update_delete()`) raises on any attempt, per the explicit "never overwrite, preserve history" product requirement. None of these three tables exist yet (they belong to later modules); when they're created, follow the pattern already established for `otp_codes`/`user_sessions` and add the trigger in that same migration, plus a `REVOKE UPDATE, DELETE ... FROM app_user` (see the comment left for this in migration `0002`).

**New tables don't need their own grants migration.** Migration `0002`'s `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ... TO app_user` applies to any table a later migration creates (confirmed working in migration `0003` — `branches`/`tenant_settings` needed no explicit `GRANT`), as long as that migration runs under the same DB role (the `postgres` superuser via `DATABASE_URL_SYNC`) that ran `ALTER DEFAULT PRIVILEGES` in the first place. Don't add per-table `GRANT ... TO app_user` statements out of habit.

**Read-vs-write permission split isn't uniform across a module — check what the data actually is.** In Tenancy, branch reads are open to any authenticated staff (operational reference data everyone needs — scheduling, check-in) while clinic settings reads are Owner-only (`clinic.manage_settings`, administrative/config data). Don't assume "GET routes are always open" or "always permission-gated" when adding a new module's routes — decide per resource, the way `app/modules/tenancy/router.py` does, and say why in a comment.

**Reusable test fixtures now live centrally in `tests/conftest.py`, not per-module.** `login_as(role_code=...)` and `owner_headers` (built on it) were added while testing Tenancy specifically so future modules' integration tests don't re-implement "create a staff user with role X, log in via the real endpoint, return auth headers" each time — use them instead of hand-rolling login boilerplate in a new module's tests.

**Staff account provisioning is a real invite/accept-token flow, not an Owner-set password** — `staff_invites` (table created by migration `0005`) stores only a hashed opaque token; `POST /api/v1/doctors` or `POST /api/v1/staff` creates the `User` (status `INVITED`, no `password_hash`) and returns the raw token in the response body outside `production` only (`debug_invite_token`, same placeholder-delivery pattern as OTP's `debug_code` — no Communications module exists yet to deliver it by email/SMS for real). The invited person calls `POST /api/v1/auth/accept-invite` with `{clinic_slug, token, password}` to set their password and flip to `ACTIVE`, then logs in normally via `/api/v1/auth/staff/login`. A resend (`POST /api/v1/doctors/{user_id}/invite/resend` or the `/api/v1/staff/...` equivalent) deletes any still-pending invite row for that user first, so an old leaked/previous token stops working the moment a new one is issued.

The mechanism's Python home moved once it needed a second caller: migration `0005` (Doctor Management) built `StaffInvite`/its repository/`POST /api/v1/doctors/accept-invite` inside the `doctors` module; migration `0006` (Staff Management) relocated the model, repository, and endpoint into the **Auth** module (`app/modules/auth/{models,repository,schemas,service,router}.py`) — a pure code move, no table/column change — because activating an invited account is role-agnostic, and leaving it under `/doctors` would have meant a newly-invited nurse posting to a `/doctors/...` URL. `issue_staff_invite` (a free function in `app/modules/auth/service.py`, not an `AuthService` method — it's called from within Doctor/Staff Management's own already-open `tenant_session`, not a fresh one) is the shared issuance path both modules call. `UserBranchAssignment` stayed in the `doctors` module (as `BranchAssignmentRepository`, generically named) since branch scoping isn't a credentials concern — Staff Management imports it directly rather than duplicating it. If a third module ever needs either mechanism, this is the pattern to follow.

**`users.first_name`/`last_name` didn't exist until migration `0005`.** The original schema design (migration `0001`) gave `users` no display-name field at all, only `email`/`phone` — unnoticed until Doctor Management needed to show/search a doctor by name. Added as nullable columns (existing rows, and OTP-only patient users, may have neither) and enforced as required only at the Pydantic layer for doctor creation specifically. If a future module hits a `None` where a name was assumed, check whether that `User` row predates migration `0005` or was created via a path (like the `PATIENT` OTP flow) that still never sets one.

**Audit logging is a per-module `record()` call, not a generic hook.** `app/modules/audit/service.py::record` is a free function (same shape as `issue_staff_invite`) — every mutating service method that should be audited calls it directly, passing the already-open `session` from its own `tenant_session`, so the audit row commits atomically with the change it describes. It was retrofitted into Patients (create/update/soft-delete), Doctors, and Staff (create/update/deactivate/reactivate/branch-assignment) when the module was built (migration `0007`); Tenancy (clinic settings, branches) was deliberately left un-audited for now — lower-stakes admin config, not a PHI/access-control entity. **Any new mutating endpoint on an entity that's clinically, financially, or access-control relevant should call `record()` at the point of the change** (PRD §14) — don't wait to be asked; check this note before adding a create/update/delete on Patients/Doctors/Staff-like entities (Appointments, EMR, etc. all qualify).

**The append-only trigger (`prevent_update_delete()`) has an escape valve for `app_is_platform_admin()`, added in migration `0009`.** Building the *first* append-only table (`audit_logs`, migration `0007`) exposed a real bug dormant since migration `0001`: `clinics` cascades `ON DELETE` to every tenant table including `audit_logs`, but the trigger unconditionally blocked *any* delete, cascade or not — harmless in production (nothing deletes a `clinics` row today) but broke every test's teardown once its throwaway clinic had audit-logged activity. Fixed by letting the trigger check the same `app_is_platform_admin()` flag `platform_admin_session()` sets — application code under normal `tenant_session` is still unconditionally blocked; only the already-sanctioned administrative bypass can remove these rows. **When Vitals/Prescriptions (the other two tables this trigger is reserved for) get built, this is already handled** — don't re-solve it.

**Slot availability has one source of truth: doctor `working_hours` + existing appointments — there is no separate calendar.** `AppointmentService._validate_slot` (called by every path that creates or moves an appointment) checks, in order: branch exists, doctor exists and is `ACTIVE`, the slot doesn't span midnight, the doctor's `working_hours` (JSON on `doctor_profiles`, parsed via the same `WorkingHours`/`DayHours` Pydantic model Tenancy's branches use) covers the requested day and time, and no other non-cancelled appointment for that doctor overlaps. **A doctor with no `working_hours` configured is fail-closed** — every day parses to "closed," not "open all day" — so a freshly-created doctor with no schedule set is simply unbookable until the Owner configures one; this surprised the first test written against it (had to `PATCH` a wide-open schedule onto test doctors) and will surprise whoever builds the frontend booking flow the same way if they don't set hours first.

**Row-level "own" scoping for Doctor is done by permission code, not row-level, when it comes to *booking* — a third permission gap found by this module's own tests.** Migration `0001` had granted Doctor `appointments.manage` (full write access for any patient), but the PRD §3 matrix gives Doctor only "R (own)" here. Migration `0010` revoked that grant and added `appointments.view` (read), with the Doctor row-scoping enforced in `AppointmentService.search_appointments`/`get_appointment` — any `doctor_id` filter a Doctor-role caller passes is silently overridden to their own user id, not merely validated, so a Doctor can never see another doctor's schedule by supplying a different id. **This is now the third `role_permissions` seed gap found this way (after two in migration `0004`) — treat an unexpected 403/scope leak in a new module's tests as a matrix-seed signal, not just a new-module bug**, same as the note below.

**Migration 0001's `role_permissions` seed data has had two rounds of gaps found and fixed by later modules' integration tests** (both in migration `0004`, both surfaced as unexpected 403s, not schema errors): Lab Staff/Pharmacy Staff missing `patients.view_demographics`, and Owner missing it despite having the broader `patients.view_emr`. **Treat a 403 you didn't expect in a new module's tests as a real signal to check the seed data against the PRD §3 matrix, not just a bug in the new module's router** — the matrix is the source of truth; migration 0001's seed is a first pass at it and has been wrong twice already. Fix gaps in the *current* module's migration (as `0004` did), never by editing an already-applied one.

**Check-in's queue/token reads are tenant/branch-wide for every role that has them at all — no per-doctor row-scoping, unlike Appointments.** The PRD §3 matrix marks "Appointment booking (staff-side)" as Doctor "R (own)" but marks both "Walk-in registration & check-in" and "Queue / token management" as plain Doctor "R" (no "(own)" qualifier) — a front-desk queue view is inherently a whole-branch view, not a personal schedule. `CheckInService.search_encounters`/`search_queue` do not override or row-scope any filter by the caller's identity the way `AppointmentService.search_appointments` does for Doctor. Don't copy the Appointments row-scoping pattern here by reflex — check what the matrix actually says per capability, same lesson as the read-vs-write permission split note above.

**Migration 0001's `role_permissions` seed data had a fourth gap, same shape as the first three**: Nurse was granted the full `queue.manage` (write) permission, but the PRD §3 matrix gives Nurse only "R" for both "Walk-in registration & check-in" and "Queue / token management." Migration `0011` revoked `NURSE`/`queue.manage` and added `checkin.view`/`queue.view` (read-only) granted to Owner, Doctor, Receptionist, and Nurse — Owner/Receptionist keep their existing `checkin.manage`/`queue.manage` for the write side, same "separate `.manage` and `.view` permission, both granted to the full-access roles" pattern migration `0010` established for `appointments.manage`/`appointments.view`.

**Queue token numbering is a branch+day sequence with a real concurrency guard, not just a `MAX()+1` read.** `QueueTokenRepository.issue` (`app/modules/checkin/repository.py`) takes a transaction-scoped Postgres advisory lock (`pg_advisory_xact_lock`, keyed by `branch_id`) before computing `MAX(token_number)+1` for that branch/day and inserting — otherwise two concurrent check-ins at the same branch could both read the same max and collide on the table's `UNIQUE(branch_id, token_date, token_number)` constraint, aborting one transaction instead of getting the next number. The lock auto-releases on commit/rollback, so it never needs explicit cleanup. `token_date` is computed in the app as `datetime.now(timezone.utc).date()` (not the column's `current_date` server default) so the lock/read/insert all agree on the same date value.

**A walk-in creates a full `Appointment` row retroactively, reusing the Appointments module's own repository.** Per PRD §5.1 step 3, `POST /api/v1/encounters/walk-in` calls `AppointmentRepository.create(...)` (extended in migration `0011`'s companion code change with an optional `status` override, used here to insert directly as `CHECKED_IN` rather than the default `SCHEDULED`) with `source=WALK_IN` and `scheduled_at=now()` — no future-slot validation applies, unlike staff/patient booking. `AppointmentRepository.update_status` (new, distinct from the existing `reschedule`) is what `check_in_appointment` and `mark_no_show` use to flip an existing `SCHEDULED` appointment to `CHECKED_IN`/`NO_SHOW` — `reschedule` is about moving a slot, not a day-of status transition, so reusing it for status changes would have been a misleading name at the call site.

**Cancelling an `Encounter` cascades to its `QueueToken` as `SKIPPED`, since the token state machine has no `CANCELLED` of its own.** `CheckInService.cancel_encounter` only allows this on an `OPEN` encounter (once `IN_CONSULTATION`/`COMPLETED` exist, that's the Consultation module's concern, not front desk's to undo) and moves the associated token to `SKIPPED` unless it's already `DONE`/`NO_SHOW`. Both are audited as separate `record()` calls (`encounter.cancel`, `queue_token.status_change`) since they're two distinct entities per the "one `record()` call per mutated entity" convention, even though they happen in the same request/transaction.

**Vitals is the first module besides `audit_logs` to actually use the append-only mechanism reserved since migration 0001.** Migration `0012` attaches `prevent_update_delete()` to `vitals` (same trigger `audit_logs` uses) and `REVOKE UPDATE, DELETE ON vitals FROM app_user`, belt-and-suspenders exactly like `audit_logs`. `VitalsRepository` (`app/modules/vitals/repository.py`) has no `update`/`delete` method at all — not just "unused," genuinely absent, so there's no code path that could even attempt one. `bmi` is a DB-generated column (`GENERATED ALWAYS AS ... STORED`, mapped via SQLAlchemy's `Computed(..., persisted=True)`) — `VitalsRepository.create` calls `session.refresh(reading)` after `flush()` because the ORM has no way to know a server-computed value until it's read back.

**`vitals.record`'s per-tenant "C" (configurable) permission is already correctly seeded as a static default (migration 0001: Owner/Doctor/Nurse on, Receptionist off) but there is still no Owner-facing endpoint to actually flip it per PRD §13's `permission_overrides` mechanism.** That configurability is a Clinic Settings-shaped feature (PRD §21: "Owner configures ... permission overrides (vitals, etc.)") that hasn't been built by any module so far, Vitals included — building it was out of scope for this module by the same "don't build what wasn't asked" judgment used elsewhere, not an oversight. If a future module needs it (Vitals is the PRD's own "concrete case" for why the override system exists at all — PRD §3), that's where it belongs.

**Vitals reads are tenant-wide, not row-scoped to Doctor "own patients"** — same reasoning as Check-in (migration 0011's note above): the PRD §3 "Vitals recording" matrix row has no "(own)" qualifier for Doctor the way the appointment-booking row does, so `vitals.view` doesn't filter by any doctor/patient relationship at the service layer, just by the query params a caller explicitly passes (`encounter_id`/`patient_id`/`recorded_by`/date range).

**Patient has no `vitals.view` grant, unlike the broader "Full patient EMR" matrix row's Patient "O (read)".** The "Vitals recording" row specifically marks Patient "–". A patient's own-vitals visibility is presumed to arrive with the not-yet-built EMR module (item 16), which is the PRD's actual home for patient-facing clinical record access — don't add it to Vitals by analogy with EMR without being asked; check the row that specific data belongs to, not an adjacent one.

**Consultation/Prescription's RBAC is a deliberate deviation from the PRD §3 matrix, by direct instruction — treat it differently from every prior "seed gap" fix.** Every previous permission correction in this file (migrations `0004`, `0010`, `0011`) was *migration `0001`'s seed disagreeing with the matrix*, fixed to match the matrix. Migration `0013` is the opposite: the matrix itself says Owner "R" and Nurse "–" for "Consultation, diagnosis, clinical notes" and "E-prescription" (Doctor "F own" only), and the product owner explicitly asked for "Doctor/Owner write, Doctor/Owner/Nurse read" instead. Don't "fix" this back toward the matrix in a future pass — it's the matrix that's stale here, not the seed. `docs/schema/clinic_erp_schema.sql`'s own seed data was updated to match this real end state (plus catching up `checkin.view`/`queue.view`/`vitals.view` grants from migrations `0011`/`0012` that had never been back-ported).

**`Consultation`/`Prescription` row-scoping for Doctor uses two different HTTP status codes depending on whether it's a read or a write.** `ConsultationService.get_consultation`/`get_prescription` (single-record reads) return 404 for a Doctor's mismatched-owner request — existence-hiding, the same pattern `AppointmentService.get_appointment` already established. `update_consultation`/`complete_consultation`/`issue_prescription`/`supersede_prescription` (writes) return 403 instead — the caller has the `.manage` permission bit but not ownership of this specific row, and there's no reason to hide existence from someone who already has (or just supplied) the resource's id in a write request. This split is new to this module; earlier modules never had a "permitted in general, wrong owner, but it's a write" case to distinguish (Appointments revoked Doctor's write grant entirely instead of row-scoping it).

**`Encounter`'s `IN_CONSULTATION`/`COMPLETED` transitions, reserved by Check-in's migration `0011` docstring, are now owned by `ConsultationService`** — starting a consultation requires the encounter to be `OPEN` (else 409) and moves it to `IN_CONSULTATION`; completing requires the encounter still be `IN_CONSULTATION` (else 409) and moves it to `COMPLETED` with `completed_at` set. Both transitions reuse `EncounterRepository.update_status` from the `checkin` module directly (cross-module repository reuse, same pattern Vitals already used for `EncounterRepository.get_by_id`) — no new Encounter-mutation code lives in `checkin` itself.

**Issuing a prescription requires an already-started `Consultation` for the same encounter — enforced in the service layer, not a DB FK.** The master schema's `prescriptions` table only has `encounter_id`, not `consultation_id` (per PRD §6's own entity sketch), so `PrescriptionService.issue_prescription` looks up `ConsultationRepository.get_by_encounter_id` itself and 422s if none exists, rather than relying on a foreign key that doesn't model this relationship. Row-scoping (`doctor_id`) is checked against the *consultation's* doctor, not the caller's own prior prescriptions — a Doctor can only issue against their own consultation.

**`prescription_items.medicine_id` has no foreign key yet, and the create/supersede API doesn't even accept it.** `medicines` (the Pharmacy module's catalog) doesn't exist, so migration `0013` created the column without `REFERENCES medicines(id)` — a future Pharmacy migration adds that FK via `ALTER TABLE`, not this one. Every prescription item today is `medicine_name_freetext` only; don't add a `medicine_id` field to `PrescriptionItemCreateRequest` until there's a real catalog to validate it against — accepting an unchecked UUID now would let garbage references into clinical records.

**Clinic Letterhead Configuration reuses `TenantSetting` (one well-known key, `letterhead.config`) rather than a new table** — `backend/app/modules/letterhead/service.py` wraps `TenantSettingRepository` with a typed Pydantic schema instead of exposing the raw generic JSON PUT (`clinic.manage_settings`, same as every other clinic-settings write) directly for this. **It deliberately does not render a PDF or image anywhere** — there is no PDF-generation or object-storage (S3/R2) library or config in this backend at all yet; that's the PRD's own Documents module (§9), a separate, later concern. `GET /api/v1/letterhead/resolve` only returns *layout parameters* (a header/footer block or null, plus margins) for a frontend to render/print with. `GET .../config` and `GET .../resolve` are open to any authenticated staff member (not `clinic.manage_settings`-gated) — same "operational reference data everyone needs" reasoning as Branches, since whoever is about to print something (not just the Owner who configured it) needs to resolve the layout.

**A real SQLAlchemy pitfall surfaced by this module's own integration tests, worth knowing before it bites another module**: calling a repository's `get_by_id` more than once for the *same row within one request* (e.g. fetch → mutate a child collection via a separate INSERT → fetch again to build the response) can silently return a **stale** `selectinload`-loaded collection — SQLAlchemy's identity map skips re-querying an already-loaded relationship on an object it already has, even though the underlying DB row's children changed via a raw `session.add()`/`flush()` in between. `InvoiceRepository._with_relations` fixes this with `.execution_options(populate_existing=True)` on every `get_by_id`/`search` query. Any future module whose service re-fetches the same aggregate root more than once per request (rather than mutating the already-loaded Python object in place) needs the same fix — this one shipped broken from a first read of the code and was only caught because the test suite actually re-fetched after mutating, which three of the four bugs the first full billing test run caught (see git history) came from.

**A recurring `Decimal` precision footgun, hit in both Billing and Reports: `sum(empty_iterable, Decimal("0"))` and `COALESCE(SUM(numeric_col), 0)` both silently drop to scale 0 ("0" instead of "0.00"), unlike a real aggregate over ≥1 row.** Python's `Decimal("0")` has no fractional digits, so summing zero items with it as the start value returns `Decimal("0")`; the exact same thing happens in Postgres when `COALESCE`'s fallback literal `0` fires because `SUM()` returned `NULL` over zero matching rows — the literal doesn't inherit the summed column's `numeric(12,2)` scale the way a real `SUM()` would. Both `BillingService._to_summary` (`app/modules/billing/service.py`) and `ReportsService`/`ReportsRepository.sum_billed` (`app/modules/reports/`) hit this — fixed by seeding Python sums with `Decimal("0.00")` and `.quantize(Decimal("0.01"))`-ing any DB-side `COALESCE(SUM(...), 0)` result. **Any future module that sums a `numeric(_,2)` column and might legitimately get zero matching rows needs the same treatment** — don't assume a bare `Decimal(str(db_value))` conversion preserves 2-decimal formatting in the empty case; it doesn't until you enforce it explicitly.

**`GET /api/v1/reports/financial`'s `date_from`/`date_to` are ISO-8601 UTC datetimes with a `+00:00` offset — pass them via a request library's query-param encoding (e.g. httpx's `params=`), never hand-built into a URL string.** A raw, un-percent-encoded `+` in a query string decodes to a space server-side (a URL-encoding convention older than JSON, still honored by every stack in this chain), silently corrupting the datetime and producing a 422 that looks like a validation bug in the endpoint rather than a client-side encoding mistake. This bit the integration test suite itself before it bit any real caller — worth remembering for any future endpoint accepting a timezone-aware datetime as a query param, not just this one.

**Pharmacy fulfills a promise Consultation's migration `0013` made, and reaches back into that already-shipped module to do it — expected, not a regression.** `prescription_items.medicine_id` was created without its FK because `medicines` didn't exist yet, with an explicit note-to-self to add the constraint once it did; migration `0017` does exactly that via `ALTER TABLE`. `PrescriptionItemCreateRequest` (`app/modules/consultation/schemas.py`) now accepts an optional `medicine_id` alongside `medicine_name_freetext` (at least one required, matching the DB `CHECK`), and `PrescriptionService.issue_prescription`/`supersede_prescription` (`app/modules/consultation/service.py`) validate any supplied `medicine_id` against the tenant's catalog via a new `_validate_catalog_medicine_ids` helper that imports `pharmacy`'s `MedicineRepository` — a forward dependency (an earlier module importing from a later one), the same kind Vitals/Billing/Reports/EMR already established reaching into Check-in/Consultation. **FEFO dispensing is safe under concurrency via an atomic conditional `UPDATE`, not a lock.** `MedicineBatchRepository.decrement_stock` runs `UPDATE medicine_batches SET quantity_on_hand = quantity_on_hand - :qty WHERE id = :id AND quantity_on_hand >= :qty` and checks the affected row count — if a concurrent dispense already drained the batch between this module's FEFO read and this UPDATE, zero rows match, the method returns `False`, and `PharmacyService.dispense_prescription_item` aborts the whole request (409) rather than partially dispensing. This is the same "let Postgres re-validate against the live value, not the value we read earlier" pattern Check-in's queue-token-numbering advisory lock solves differently (that one serializes issuance; this one just fails closed) — pick whichever fits: serialize-and-retry when the operation should always eventually succeed (numbering), fail-fast when "someone else got there first" is a legitimate, reportable outcome (dispensing against finite stock).

**A second real SQLAlchemy pitfall, different from Billing's staleness bug, caught by this module's own tests: an ORM-aware bulk `UPDATE` can silently *mutate* an already-loaded object's in-memory attribute to match the new value — not just leave it stale.** `PrescriptionItemLookupRepository.increment_dispensed_quantity` runs `UPDATE prescription_items SET dispensed_quantity = dispensed_quantity + :delta WHERE id = :id`; SQLAlchemy's default "evaluate" synchronize-session strategy for `Session.execute(update(...))` evaluates that SET expression in Python against any already-loaded object matching the WHERE clause and patches its attribute to match — so the `PrescriptionItem` object fetched earlier in the same request had its `.dispensed_quantity` silently bumped by the UPDATE, and computing `item.dispensed_quantity + payload.quantity` afterward double-counted the delta. Fixed by re-fetching (`item_repo.get_by_id`) for the authoritative post-update value instead of trusting the in-memory object. **Combined with Billing's `populate_existing=True` fix, the lesson for future modules is: after any bulk `update()`/`delete()` executed via the ORM session, never trust an already-loaded Python object's attributes without an explicit re-fetch — SQLAlchemy may leave them stale (Billing's case) or silently "helpfully" sync them (this case), and either way the object in your hand cannot be assumed to reflect what you just wrote.**

**`app/api/deps.py::require_feature_flag()` is the first per-tenant module-wide gate in this codebase, deliberately built generic rather than Lab-specific.** Unlike `require_permission` (checks the JWT's embedded permission set, zero DB hits), it always queries `TenantSetting` fresh — a feature toggle can flip between one request and the next without waiting for a token refresh, and gating a whole module is rare enough that the extra query isn't worth optimizing away. **`FollowUp.status` can reach `OVERDUE` with no scheduler at all — it's computed lazily, swept on every read.** `FollowUpRepository.sweep_overdue` runs a single `UPDATE ... WHERE status IN ('PENDING','SENT') AND due_at < now()` before every search/get in `FollowUpService`, not on a timer — there is no background-job/task-queue infrastructure anywhere in this backend yet (PRD §10 itself leaves the task-queue library choice as "not blocking this document," i.e., never actually decided). **CRM's Doctor RBAC is a direct instruction deviation, not a gap-fix — the PRD §3 matrix gives Doctor "–" (no access at all) on "CRM, leads, follow-ups," full stop.** The product owner explicitly asked for Doctor to schedule and see their own follow-ups ("from doctor desk or reception," "scoped to their own follow-up patients"). **General (Non-Medicine) Inventory (`inventory_items`/`inventory_transactions`, migration `0022`) is a genuinely separate ledger from Pharmacy's `medicines`/`medicine_batches`/`pharmacy_inventory_transactions` — don't conflate the two or try to unify them.** Pharmacy's tables are medicine-specific (FEFO batches, expiry dates, prescription linkage); this module covers everything else a clinic stocks — consumables, equipment, lab supplies, office supplies — with no expiry/batch concept at all, just a single running `current_stock` per item. **`inventory_transactions.change_type` is a wholly new `inventory_change_type` enum (`PURCHASE`/`USAGE`/`ADJUSTMENT`/`RETURN`), deliberately not a reuse of Pharmacy's existing `inventory_txn_type` (`RECEIVE`/`DISPENSE`/`SALE`/`ADJUST`/`EXPIRE_WRITE_OFF`).** Both enums serve conceptually similar "why did stock change" purposes, but this task's own 4-value vocabulary doesn't map cleanly onto Pharmacy's (there's no `SALE`/`DISPENSE` concept here, and Pharmacy has no `RETURN`) — forcing a shared enum would have meant one domain inheriting values meaningless to it. First creation, no `ALTER TYPE` needed. `quantity` on the transaction row stores the caller's submitted magnitude as-is (always positive for `PURCHASE`/`USAGE`/`RETURN`; either sign only for `ADJUSTMENT`) rather than a pre-signed delta — `change_type` plus `quantity` together fully describe the movement, and `InventoryService.record_transaction` derives the signed delta (`-quantity` for `USAGE`, `+quantity` for everything else including `ADJUSTMENT`, which the schema validator already constrains to nonzero-either-sign) applied to `current_stock`.

**The negative-stock guard reuses Pharmacy's exact "atomic conditional UPDATE, no explicit lock" pattern, not a fresh design.** `InventoryItemRepository.apply_delta` runs `UPDATE inventory_items SET current_stock = current_stock + :delta WHERE id = :id AND current_stock + :delta >= 0` and checks the affected row count — the same "let Postgres re-validate against the live value at UPDATE time, not whatever the app read earlier" principle as `MedicineBatchRepository.decrement_stock`, just generalized to work for both directions of a signed delta in one method instead of a decrement-only one. A `CHECK (current_stock >= 0)` on the table itself is belt-and-suspenders behind that, same as `medicine_batches.quantity_on_hand`'s own CHECK.

**RBAC here is a direct product-owner deviation from the PRD §3 matrix, not a gap-fix — the matrix's "General inventory & expenses" row gives everyone but Owner "–" (Other Staff a configurable "C"), full stop.** The product owner explicitly asked for Receptionist/Nurse/(Other Staff, the matrix's own "Staff" tier) to read items and log `USAGE` transactions specifically — not `PURCHASE`/`ADJUSTMENT`/`RETURN`, which stay Owner-only — and for Doctor to be read-only. Two new permissions: `inventory.view` (Doctor) and `inventory.record_usage` (Receptionist/Nurse/Other Staff). **The `USAGE`-only restriction can't live at the route-permission layer the way Expenses' `.manage`/`.record` split does**, because Expenses could put the Owner-only write on a *separate* `PATCH` route, while here all four `change_type`s share one `POST .../transactions` route — so `InventoryService.record_transaction` checks `actor_role != "OWNER"` itself and 403s any non-`USAGE` attempt, after the route's `require_any_permission("inventory.manage", "inventory.record_usage")` has already let the caller through. "Owner/Admin" in the task's own wording collapses to the single `OWNER` role code — no separate "Admin" role exists in this system's 8-role model.

**Item creation deliberately has no `current_stock` field at all — every item starts at zero and stock only ever enters via a `PURCHASE` transaction.** Same "stock is a ledger, not a value you set" discipline Pharmacy's `Medicine` (starts with no batches, hence zero total stock) already established. `InventoryItemUpdateRequest` likewise has no `current_stock` field — metadata edits (`name`/`category`/`unit`/`min_reorder_level`/`cost_per_unit`/`is_active`) go through `PATCH .../items/{id}`, but the running balance is only ever touched by `record_transaction`'s atomic delta. This `PATCH` route itself is not named in the task's own 4-endpoint list — it was added because RBAC section 3 explicitly says "Owner/Admin: Full CRUD," and there was otherwise no way to reach the "U" in CRUD (no delete route was added either — `is_active` toggling via this same `PATCH` covers the "D," the same soft-delete-via-flag precedent `Medicine.is_active` already set, so a hard DELETE was never needed). All 575 tests passed, zero regressions against the prior 553 baseline.

**`leads.status`'s new `lead_status` enum deliberately does not reuse the master schema's already-sketched `lead_stage` — don't "fix" this into a shared type later without checking the value sets first.** `lead_stage` (`NEW`/`CONTACTED`/`QUALIFIED`/`CONVERTED`/`LOST`) had been sitting in `docs/schema/clinic_erp_schema.sql`'s enum block since the file's original draft, but no migration before `0023` ever actually created `leads` — so `lead_stage` was never a live Postgres type, just a doc-only placeholder. This task's own vocabulary swaps `QUALIFIED` for `APPOINTMENT_SCHEDULED`, a genuinely different value, so migration `0023` created a fresh `lead_status` type instead of reusing/renaming `lead_stage` — and the doc's now-orphaned `lead_stage` line was removed entirely (not left as a stale, unreferenced type that might mislead a future reader into thinking something still uses it).

**`convert_lead` talks to `PatientRepository` directly, inside its own `tenant_session`, rather than calling `PatientService.create_patient` — a deliberate choice to keep the module-boundary-crossing pattern consistent with every other module in this codebase.** Every existing cross-module reach in this backend (Vitals → Check-in's `EncounterRepository`, Pharmacy → Consultation's `PrescriptionItem`, Reports → Billing/Consultation's join shape, CRM → Patients/Doctors/Check-in repositories) stays at the Repository/model level; none of them calls another module's *Service* class. Doing so here too means lead-conversion is genuinely atomic in one transaction (the new `Patient` row and the lead's `status=CONVERTED`/`converted_patient_id` update commit or roll back together) — calling `PatientService.create_patient` instead would have split this across that service's own separately-managed sessions, the same non-atomic shape `PatientService` itself already accepts internally (a duplicate-check session, then a create session), which would have been a strictly worse guarantee for this specific flow. The auto-MRN-generation and up-to-5-attempts collision retry are duplicated from `PatientService.create_patient` rather than extracted into a shared helper — the same "each module keeps its own small helpers" judgment call Reports made for its doctor-ownership join.

**A lead can only be converted from `NEW`/`CONTACTED`/`APPOINTMENT_SCHEDULED`, and only if it has a phone number or email address — both checked in `LeadService.convert_lead` before touching `PatientRepository` at all, not left to `PatientCreateRequest`'s own validation to surface as a confusing generic error.** Converting an already-`CONVERTED` or `LOST` lead is a 409 ("Cannot convert a lead that is already ..."); a lead with neither contact field is a 422 with a domain-specific message. `LeadUpdateRequest` separately blocks setting `status` to `CONVERTED` directly via `PATCH` (422, "Use POST /leads/{id}/convert...") — that transition is only ever allowed through the dedicated endpoint, the same "status is always derived, never set directly except at specific transition points" principle Billing's `Invoice.status` established, applied here to prevent a `CONVERTED` lead with no `converted_patient_id` ever existing.

**RBAC here is a direct product-owner deviation from the PRD §3 matrix, and deliberately does NOT reuse the existing `crm.manage` permission despite the matrix modeling "CRM, leads, follow-ups" as one combined row.** Doctor already holds `crm.manage` (Owner/Receptionist/Doctor-for-their-own-follow-ups, since migration `0019`'s own deviation) — if Leads' routes were gated by that same code, Doctor would have silently gained *write* access to leads too, since permission checks are per-code membership, not per-resource. This task explicitly wants Doctor read-only on leads, a different tier than their follow-ups access, so two new, leads-specific permissions were added instead: `leads.manage` (Owner/Receptionist) and `leads.view` (Doctor). Nurse/Lab Staff/Pharmacy Staff/Other Staff/Patient hold neither — zero access, matching the matrix's "–" (Other Staff's matrix "C" was never asked for here, unlike General Inventory's task explicitly naming "Staff"). All 617 tests passed, zero regressions against the prior 575 baseline.

**`CommChannel`/`CommStatus`/`CommunicationLog` moved from `app.modules.crm.models` to a new `app.modules.notifications.models` in migration 0024 — a pure code move, no table/column change, same "relocate once it needs a second caller" precedent `StaffInvite` set moving from `doctors` to `auth`.** Follow-ups (CRM) was the only writer to `communication_logs` until this module existed; now Appointments, Billing, Lab, and CRM all dispatch through it, so Notifications — not CRM — is the concept's true owner. `app/modules/crm/models.py` keeps only `FollowUpStatus`/`FollowUp`; it imports `CommunicationLog` from `notifications.models` solely for the `FollowUp.reminder` relationship's string type annotation, nothing re-exported. `crm/repository.py`'s own `CommunicationLogRepository` was deleted outright (not deprecated) — its one method moved to `notifications/repository.py` verbatim. If a test or module still imports `CommunicationLog` from `crm.models`, it's relying on an incidental namespace leak from that annotation-only import, not a deliberate re-export — don't rely on it; import from `notifications.models` directly (this bit `tests/tenant_isolation/test_crm_tenant_isolation.py` during this module's own build, fixed the same session).

**`dispatch_notification()` is a free function, not a service method — same "caller supplies the already-open `tenant_session`" pattern as `record_audit`/`issue_staff_invite`, chosen for the same reason: it needs to commit atomically with whatever business event triggered it** (an appointment booking, a payment, a lab order completing, a follow-up being created), inside that caller's own transaction, not a separate one. It auto-enriches the caller's `context` dict with `clinic_name` (via `ClinicRepository`) and, when a `patient_id` is supplied, `patient_name` (via `PatientRepository`) — every one of the four call sites already had `patient_id` on hand for free (`Appointment.patient_id`, `Invoice.patient_id`, `LabOrder.patient_id`, `FollowUp`'s own `payload.patient_id`), so none of them need to look up a name themselves. Looking up an active `NotificationTemplate` for `(tenant_id, channel, template_key)` and falling back to `_DEFAULT_TEMPLATE_BODIES[template_key]` when the Owner hasn't customized that trigger yet means a fresh clinic gets sensible queued messages out of the box, not silence — `template_key` is deliberately not validated against a closed set (see below), so an unrecognized key with no clinic template renders an empty body rather than raising.

**`template_key` is free text, not a closed enum — this task's own wording ("e.g. APPOINTMENT_BOOKED, ...") signals a non-exhaustive, extensible set, and the master schema's own original sketch (`event_key text`) already had the same "open string" design intent, just dot-separated instead of this task's `UPPER_SNAKE_CASE`.** Don't add a Postgres enum or a Pydantic `Literal` restricting it later without checking this reasoning first — a clinic (or a future business module) should be able to introduce a new trigger key without a migration. The 5 keys this task named (`APPOINTMENT_BOOKED`/`APPOINTMENT_REMINDER`/`BILL_RECEIPT`/`LAB_RESULT_READY`/`FOLLOW_UP_REMINDER`) exist as plain string literals at their call sites and as `_DEFAULT_TEMPLATE_BODIES` dict keys in `notifications/service.py` — not as a shared constants class, matching how audit `action` strings (`"lead.create"`, `"payment.record"`, ...) are plain literals throughout this codebase rather than a shared enum.

**Business-trigger integration was kept to one line-level `dispatch_notification()` call added at an existing success path in each of Appointments/Billing/Lab/CRM — no method signature changed, no response shape changed, in any of the four modules.** Appointments' `_create` (fires for every booking path — receptionist, patient self-booking — since `create_appointment`/`create_my_appointment` both funnel through it) dispatches `APPOINTMENT_BOOKED` with `appointment_time` in context. Billing's `PaymentService.record_payment` dispatches `BILL_RECEIPT` only `if payload.amount > 0` — a negative amount is a refund/reversal (per Billing's own existing convention), which isn't a receipt and shouldn't queue one. Lab's `LabOrderService.complete_order` dispatches `LAB_RESULT_READY` with `test_name` taken from the already-`selectinload`-ed `order.test` relationship (no extra query). CRM's `FollowUpService.create_follow_up` now calls `dispatch_notification` with `template_key="FOLLOW_UP_REMINDER"` instead of inserting a bare `CommunicationLog` stub directly — the caller-supplied `payload.channel` is passed through unchanged, so a clinic-configured `FOLLOW_UP_REMINDER` template now actually applies to follow-up reminders too, which it never could before this module existed. All four modules' existing test suites (74 tests total) were re-run after these changes and still pass unmodified — confirming the integration is genuinely additive.

**Notification template CRUD deliberately has no `record_audit` calls, unlike almost every other mutating endpoint built this session.** A template is admin config — wording and an on/off toggle for an outbound message — the same "lower-stakes admin config, not a PHI/access-control entity" category Tenancy's clinic settings/branches were left un-audited for from the start. Don't add audit calls here by reflexive pattern-matching against Leads/Inventory/Pharmacy's own mutating endpoints without checking this reasoning first — those are patient-facing or financial/access-control entities; a notification template's wording is not.

**These two features (Permission Override write endpoint, File Storage & Uploads) came out of a PRD-vs-codebase audit, not the normal "next module in §10's list" build order — treat them as gap closures, not a new module pair, when reading git history.** Both were flagged as the two highest-value gaps blocking real frontend work: an Owner Settings screen that toggles permissions has nowhere to save to without the first, and any document-upload screen (patient records, lab reports, letterhead branding) has nowhere to actually send bytes without the second.

**The Permission Override write endpoint needed zero migration** — `permission_overrides`, its `CHECK` constraint, and both partial unique indexes have existed since migration `0001`; `PermissionRepository.resolve_effective_permissions` has been reading them into every JWT since then too. Only the write path was missing. `PermissionOverrideService.set_override` upserts via get-then-update-or-insert against `PermissionOverrideRepository.get_for_role`/`get_for_user` — a real race between two concurrent PUTs for the same target would hit the DB's own unique index and fail one of them, the same acceptable-risk level `TenantSettingRepository.upsert` already accepts for admin-configuration writes (not a payments/inventory-shaped correctness concern). `RoleRepository`/`PermissionRepository.get_by_code` resolve `role_code`/`permission_code` to ids with a 422 on an unknown value, so a request never reaches Postgres with a dangling reference. Gated by the pre-existing `staff.manage` — deliberately not a new permission code, since PRD §3's own "Staff, roles & permissions" row already describes exactly this capability and Owner already holds it.

**File Storage & Uploads deliberately does NOT touch any existing module's schema** (`medical_documents`, Letterhead's `header_image_url`/`footer_image_url`, `expenses.receipt_document_id`) — all three were already generic string/URL pointer fields with nothing behind them; this module is purely the thing that makes a pointer resolvable to real bytes for the first time; wiring an existing module's own create/update payload to actually populate its pointer field with a returned `download_url` is left for whenever a frontend needs it, not built preemptively here. `app/core/storage.py`'s `FileStorageBackend` is an `ABC` with exactly one working implementation (`LocalFileStorageBackend`) — `get_storage_backend()` raises `NotImplementedError` with a clear message for any other configured value rather than silently no-op'ing, so a future S3/R2 backend has an obvious single seam to implement against, and a misconfigured environment fails loud at first use, not silently.

**Authorization for the generic `/api/v1/files/*` endpoints is dispatched per-`owner_type` inside the service, not gated by a single permission at the router** — unlike every other module, there is no one capability that legitimately covers all three owner kinds this module serves (`PATIENT_DOCUMENT`, `LAB_REPORT`, `LETTERHEAD_ASSET`), so the router only requires authentication and `FileService` looks up `_WRITE_PERMISSION_BY_OWNER_TYPE`/`_READ_PERMISSION_BY_OWNER_TYPE` (plain module-level dicts, three entries each) to find the real permission for the specific document in question. **Reads additionally replicate row-level scoping from each source module rather than inventing new logic**: `PATIENT_DOCUMENT` reuses `EmrRepository.doctor_has_treated_patient` (Doctor) and a Patient-self `PatientRepository.get_by_user_id` match (Patient); `LAB_REPORT` reuses Lab's own "Patient sees only their own `COMPLETED` order's report" rule. Skipping this replication would have made the new generic registry a side-channel that bypasses access rules those modules already got right — e.g. a Patient could otherwise read another patient's document by guessing a `document_id`, since `patients.view_emr` alone (the coarse permission check) doesn't encode *which* patient. A row-scope mismatch on a read is 404, not 403 — existence-hiding, the same convention `AppointmentService`/`EmrService` already established for "wrong owner." Adding a fourth `owner_type` later means adding one entry to each of the two permission dicts and, if it needs row-scoping, one branch in `_row_scope_allows` — not a migration, and not a new permission code unless the new context genuinely doesn't already have one.

**`LocalFileStorageBackend`'s key-traversal guard is real, not decorative** — a `storage_key` containing `../` segments is rejected before ever touching the filesystem, even though every caller in this codebase constructs the key itself (`{tenant_id}/{owner_type}/{owner_id}/{uuid}-{filename}`, never from raw user input) and so could not currently trigger it. Defense-in-depth for a mistake that hasn't happened yet, not a response to an observed one — worth keeping if a future caller ever builds a key from a less-trusted input than it does today. All 697 tests passed (41 new: 18 for the Permission Override endpoint, 23 for File Storage & Uploads), zero regressions against the prior 656 baseline.

**This session's four "final bridges" (Prescription PDF, SMS/WhatsApp adapter, Payment gateway adapter, ABHA/ABDM prep) came from a direct product-owner ask to close specific PRD-vs-codebase gaps identified in an earlier audit, not from §10's module-by-module build order — same "gap closure, not a new module" framing as the Permission Override/File Storage pair before them.** Read them together: three of the four (Prescription PDF, SMS/WhatsApp, Payment Gateway) are "plumbing that was completely missing" fixes: the pipe now exists end-to-end, but every real destination (an actual SMS/WhatsApp provider, an actual payment gateway) is still a `Console`/`Mock` placeholder. Don't mistake "adapter interface exists and is tested" for "this sends a real WhatsApp message" or "this can actually take a customer's money" — neither is true yet, by design, until a real provider is configured.

**Every one of the three adapter/gateway stubs follows the exact same three-piece shape, deliberately, so they're easy to reason about together**: (1) a `Protocol` interface (`ChannelAdapter`, `PaymentGatewayAdapter`, and `FileStorageBackend` before them) with a single async method: (2) exactly one concrete implementation (`ConsoleChannelAdapter`, `MockPaymentGatewayAdapter`, `LocalFileStorageBackend`) that never talks to a real network and always simulates success; (3) a `get_*_adapter()`/`get_*_backend()` factory reading one `Settings` field (default `"console"`/`"mock"`/`"local"`), raising `NotImplementedError` with a specific message for anything else rather than silently no-op'ing. Adding a real provider later means writing one new class implementing the interface and one new `elif` branch in the factory — zero changes to any caller. Don't reach for a heavier plugin-registry/entry-points mechanism if a fourth adapter is ever needed; this three-piece shape is the established pattern.

**Both `ConsoleChannelAdapter` and `MockPaymentGatewayAdapter` are synchronous, direct-dispatch calls inside the same DB transaction as the business action that triggers them — not `FastAPI BackgroundTasks`, by explicit instruction and for a real reason, not just convenience.** PRD §16 itself says notification sending "must never block" the triggering request, which argues for deferring it — but deferring to `BackgroundTasks` means it runs *after* the response is already sent, using a *new* DB session, which would break this codebase's own established convention that a business action, its audit trail, and (now) its notification dispatch all commit or roll back together as one atomic unit. Given every adapter today is instant and local (a log line, not a network call), there is no latency to hide yet, so direct dispatch has no real downside and preserves that atomicity. **This tradeoff is specifically worth revisiting the day a real provider is wired in** (a real Twilio/Gupshup/Razorpay call has real network latency and can hang or fail) — that is the moment `BackgroundTasks` or a real queue earns its complexity, not before.

**Prescription PDF's `_generate_and_store_prescription_pdf` calls three other repositories it doesn't otherwise need (`PatientRepository`, `UserRepository`, `MedicineRepository`) purely to resolve display names/labels for the rendered document — this is the correct amount of coupling for a rendering helper, not scope creep.** A PDF a patient/doctor actually reads needs a real patient name and doctor name, not raw UUIDs; a prescription item's `medicine_name_freetext` is only ever populated for non-catalog medicines (the DB `CHECK` requires exactly one of `medicine_id`/`medicine_name_freetext`), so a catalog-linked item genuinely has no display name anywhere else in the already-fetched data and must be looked up. Don't "simplify" this by dropping the catalog lookup and just printing a medicine_id — that would ship a prescription no one asked for.

**`app/modules/files/service.py::store_generated_document` deliberately bypasses `FileService.upload`'s own per-`owner_type` permission dispatch — this is not an oversight, it's why `PRESCRIPTION_PDF` is only ever in `_READ_PERMISSION_BY_OWNER_TYPE`, never `_WRITE_PERMISSION_BY_OWNER_TYPE`.** The generic upload endpoint's permission check exists to authorize an *end user's* upload request; a server-generated PDF isn't an upload request at all, it's the trusted output of a business action (`issue_prescription`) whose own authorization (Doctor issuing their own prescription, or Owner) already happened upstream. Checking a permission a second time here would be redundant at best and wrong at worst (there's no natural "permission to upload a PRESCRIPTION_PDF" for a caller to hold, since the caller isn't the one deciding to create it — the business logic is). If a future server-generated document type is added, give it the same treatment: a free function that calls the storage backend + `DocumentRepository` directly, not a call through `FileService.upload`.

## Frontend architecture notes

**Frontend scaffolding (Step 6) pivoted `frontend/` from the old single-tenant demo to a fresh Vite app rather than trying to evolve the demo in place — same "rename, don't delete or mutate" precedent as `backend-legacy-node-scaffold/`.** The demo now lives at `frontend-legacy-demo/`, untouched and unreferenced by anything current. `frontend/package.json`'s `dev`/`build`/`test` script names were kept identical to what the demo had, so the root `package.json`'s `npm --prefix frontend run dev/build/test` still works unchanged — no root-level script needed updating.

**Tailwind is v4, configured CSS-first — there is no `tailwind.config.js` anywhere in `frontend/`, by design, not an oversight.** `@tailwindcss/vite` is a Vite plugin (`vite.config.ts`), and every design token (colors, radius) lives as CSS custom properties directly in `src/index.css` under `@theme inline`/`:root`/`.dark` — this is Tailwind v4's own recommended setup, not a simplification. Don't add a `tailwind.config.ts` "to be safe"; it won't be picked up by `@tailwindcss/vite` and would just be dead weight.

**shadcn/ui here is the `base-nova` style, built on `@base-ui/react` (MUI's unstyled primitives library), not the classic Radix UI + hand-rolled `cn()` combo most shadcn docs/tutorials still show.** This is whatever `npx shadcn@latest init` resolved to at scaffold time (2026-09) — the CLI's registry has moved on from Radix as the default primitive layer. `cn()` itself is imported from the `cn` npm package (`src/lib/utils.ts` just re-exports it), not hand-written with `clsx`+`tailwind-merge` the older way, even though both of those are still installed as `cn`'s own dependencies. When adding a new shadcn component, always use `npx shadcn@latest add <name>` rather than hand-copying an older Radix-based example off the docs site — the generated code imports from `@base-ui/react/*`, and a hand-copied Radix version simply won't match this project's primitive layer.

**The `@/*` path alias needs configuring in three places to actually work, and TypeScript 6.0 deprecated `baseUrl`** — `tsconfig.json`/`tsconfig.app.json`'s `compilerOptions.paths` (for the TS compiler and editor tooling) and `vite.config.ts`'s `resolve.alias` (for Vite's own bundling, which doesn't read tsconfig `paths` at all) both need the same mapping; `baseUrl` was deliberately left out of both tsconfig files (TS 6's `moduleResolution: "bundler"` resolves `paths` relative to the tsconfig file itself without it) — adding `baseUrl` back in would just reintroduce `TS5101`'s deprecation error at build time.

**The frontend dev server is pinned to port 3000 (`vite.config.ts`'s `server.port`), not Vite's own default 5173 — to match the backend's existing `CORS_ORIGINS` default (`["http://localhost:3000"]`, `backend/app/core/config.py`) without touching backend config for a frontend-only concern.** If a future need (running both the legacy demo and the new app simultaneously, e.g.) forces a different frontend port, update `backend/.env`'s `CORS_ORIGINS` rather than fighting over port 3000 — don't silently let CORS start failing.

**The Axios client (`src/lib/api-client.ts`) and its token storage (`src/lib/token-storage.ts`) persist `clinic_slug` alongside the access/refresh tokens — not just the two tokens — because the backend's own `staff/refresh` and `staff/logout` endpoints require `clinic_slug` in the request body, not just a bearer token** (see `backend/app/modules/auth/schemas.py`'s `RefreshRequest`/`LogoutRequest` — there's no subdomain-based tenant resolution in this codebase yet, so the slug has to come from somewhere client-side once the original login form is gone). A session is only considered "present" (`getStoredSession()`) when all three values exist together; losing any one of them is treated as no session at all. **Whoever builds the real login screen must keep collecting/persisting `clinic_slug` at login time** — don't "simplify" it away as redundant with the JWT without checking this constraint first.

**401 handling coalesces concurrent failures onto a single in-flight refresh call, and talks to the refresh endpoint through a bare second Axios instance (`refreshClient`) instead of `apiClient` itself, to avoid the response interceptor recursing into itself.** A request whose URL is in `AUTH_EXEMPT_PATHS` (login, refresh, OTP request/verify, accept-invite) never gets a bearer token attached and never triggers the refresh-and-retry dance on a 401 — a 401 from one of those endpoints is the real, final answer (wrong password, expired OTP), not a stale-access-token situation to paper over.

**Session expiry is communicated out of the Axios layer via a plain `window` custom event (`src/lib/auth-events.ts`), not a callback injected into the client or a shared store import, specifically so `api-client.ts` has zero dependency on React/React Router.** `AuthProvider` is the only subscriber (`onSessionExpired(clearSession)`); a failed refresh clears storage and fires the event, `AuthProvider` reacts by dropping to `unauthenticated`, and `RequireAuth` (`src/routes/require-auth.tsx`) is what actually performs the `<Navigate to="/login">` redirect — the interceptor itself never touches routing.

**`LoginPage`/`DashboardPage` (`src/pages/`) are placeholders proving the skeleton wires together end to end (real login against the actual backend, real permission list rendering, real logout) — not the start of the real page-by-page build.** Don't extend either of these into real screens without being asked.

**Patient search (`src/features/patients/search-classifier.ts`) can't just forward one search box's text to all three of `q`/`phone`/`mrn` at once — the backend ANDs whatever filters are supplied and `phone`/`mrn` are exact matches, not partial (`backend/app/modules/patients/repository.py`).** `classifyPatientSearchTerm` guesses a single field from the typed text (fully phone-shaped → `phone`; no spaces + has a digit + MRN-shaped → `mrn`; else → `q`, trigram-fuzzy on the backend). This means phone search only ever matches once the *whole* number is typed — an inherent backend constraint, not a frontend bug — don't "fix" this into per-keystroke partial phone matching without changing the backend's own exact-match filter first.

**The optional doctor picker in `NewPatientDialog`'s check-in section only renders when `hasPermission('doctors.view_directory')` — and OWNER genuinely does not hold that permission** (migration `0008` granted it to Receptionist and Patient only, for booking flows; see `backend/app/modules/doctors/router.py`'s own docstring). An Owner logged in and registering a walk-in simply won't see a doctor selector and will check the patient in with `doctor_id` unset — this matches the backend's own "a walk-in may arrive before front desk has assigned a doctor" design, not a frontend gap. Don't add a client-side permission bypass to "fix" this; if Owner should see the directory, that's a backend permission-matrix change to make deliberately, the same way every other permission gap in this codebase has been fixed.

**Staff Directory (`/staff`) has no single backend endpoint — it merges two separately-permissioned queries client-side** (`GET /api/v1/staff` for the 5 non-doctor staff roles, `GET /api/v1/doctors` for doctors; both gated by the same Owner-only `staff.manage`), sorted together into one `DirectoryRow[]` in `staff-directory-page.tsx`. The "Invite staff" modal (`src/components/staff/invite-staff-dialog.tsx`) similarly dispatches to `POST /api/v1/staff` or `POST /api/v1/doctors` depending on the selected role — there is no unified "create person" backend endpoint, by design (a doctor's fields — specialization, consultation fee — genuinely differ from a staff member's). A created invite's `debug_invite_token` (present only outside `production`, same placeholder-delivery convention as OTP) is surfaced directly in the dialog's success view since there's still no real email/SMS provider to deliver it.

**`NewPatientDialog`'s "Age (years)" field is a convenience-only input, never sent to the backend** — `resolveDateOfBirth()` converts it to an approximate `date_of_birth` (Jan 1 of the computed birth year) on submit, since many walk-in patients don't know their exact DOB but do know their age. If both Age and Date of birth are filled, the exact DOB wins.

**The OPD Queue (`/opd`) has no single backend endpoint that returns "today's queue with patient names" — `src/features/opd/use-doctor-queue.ts` joins three levels client-side: `GET /queue?doctor_id=<self>` → per-token `GET /encounters/{encounter_id}` → per-encounter `GET /patients/{patient_id}`, the last two levels fetched in parallel via `useQueries`.** `QueueTokenSummary` only carries `encounter_id`; `EncounterSummary` only carries `patient_id` — neither embeds a display name (`backend/app/modules/checkin/schemas.py`). This is an N+1 pattern, deliberately accepted rather than asking for a backend change mid-frontend-task: bounded by one doctor's realistically-small daily queue, not a bulk admin list. `search_queue` also has no date filter and only accepts one `status` value at a time (not a list), so filtering to "today, and still WAITING/CALLED/IN_PROGRESS" happens entirely client-side (`ACTIVE_QUEUE_STATUSES`, `token_date === today`) rather than via query params — don't add a `status[]` array param assumption when touching this hook, the backend genuinely doesn't support it.

**Doctor does NOT hold `queue.manage` — only `queue.view` — a real RBAC boundary confirmed against the running backend, not a frontend oversight.** Migration `0011`'s seed gives `queue.manage` (the permission behind `PATCH /queue/{token_id}` and `POST /queue/call-next`) to Owner/Receptionist only; Doctor and Nurse are read-only on the queue (`backend/app/modules/checkin/router.py`). So the OPD Queue page's only doctor-side action is **Start Consultation** (`POST /consultations`, gated by `consultation.manage`, which Doctor does hold per migration `0013`'s deliberate matrix deviation) — there is no "Call Patient" queue-status button anywhere in this workspace, despite the task that requested this screen describing one. Don't add a queue-token status-change button gated only by `queue.view`; it would just 403 for every Doctor who clicked it.

**`OpdWorkspacePage` resolves "the" consultation for an encounter via `GET /consultations?encounter_id=X`, not a stored consultation id, because the route is keyed by `encounterId` (from the queue), not a consultation id the queue never has.** `useConsultationByEncounter` selects `items[0] ?? null` — `null` (query settled, no match) means the encounter is `OPEN` and nobody's started a consultation for it yet, which the page handles as an inline "Start consultation" prompt rather than dead-ending; this covers both the normal path (arriving via the queue's own "Start consultation" button, which already created one) and a direct/refreshed navigation to the URL. An encounter already `COMPLETED`/`CANCELLED` renders a read-only "this encounter is completed" message instead of the pad — there's no revisit/edit flow for a finished consultation in this pass.

**The Lab Order panel and the Rx table's medicine autocomplete both degrade silently, not with an error banner, when their backend capability is unavailable — same "absent capability isn't an error state" precedent as the Patients module's doctor-directory picker.** `LabOrderPanel` returns `null` entirely if the caller lacks `lab.order`, or if `GET /lab/orders?encounter_id=...` 403s (almost always `features.lab_enabled` being off for this clinic — the whole Lab module is feature-flagged, `backend/app/modules/lab/router.py`, with no client-readable way to check the flag directly). The medicine autocomplete (`useMedicineSearch`, `retry: false`) just falls back to a plain free-text `medicine_name_freetext` entry on any failure — `pharmacy.view_catalog` reads aren't feature-flagged (only OTC *sales* are, migration `0021`), so this mainly guards against a caller genuinely lacking the permission, not a disabled module.

**Issuing the prescription (`POST /prescriptions`) is what generates the PDF — there is no separate "generate PDF" call.** `PrescriptionSummary.pdf_download_url` comes back as `"/api/v1/files/{id}/content"`, a path that already includes `/api/v1` — passing that string straight to `apiClient` (whose `baseURL` already has `/api/v1`) would double it up. `src/features/files/api.ts::downloadDocumentBlob` sidesteps this entirely by building the request from `pdf_document_id` alone, never from the `_url` string. `PrescriptionPreviewDialog` fetches the PDF as a `Blob` via `apiClient` (so the JWT interceptor attaches the bearer token — the backend's `/files/{id}/content` route requires auth and returns `Content-Disposition: attachment`, which is irrelevant once the bytes are already fetched into a JS `Blob`) and renders it via a `blob:` object URL in an `<iframe>`, with Download/Print buttons driving that same iframe — not a raw `<a href="/api/v1/files/...">` link, which would hit an unauthenticated browser navigation and fail.

**"Finish encounter & generate Rx" performs three backend calls in sequence, in a specific order, from the frontend — there is no single backend endpoint for this combined action.** `ConsultationPad.onFinalize`: (1) `PATCH /consultations/{id}` with whatever note fields are non-empty, (2) `POST /prescriptions` (requires the consultation to still be open — issuing after `complete` would find no open consultation to attach to), (3) `POST /consultations/{id}/complete`. If step 2 or 3 fails after step 1 succeeded, the notes are already saved server-side (no rollback) — acceptable here since notes are harmless to have saved early and the toast surfaces exactly which step failed; don't "fix" this into a single transactional call without adding a real backend endpoint for it first.
