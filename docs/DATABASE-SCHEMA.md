# Clinic ERP + CRM — Database Schema Overview

**Status:** implemented and migrated so far — Auth module (`backend/app/modules/auth`, migrations `0001`, `0002`): `clinics`, `roles`, `permissions`, `role_permissions`, `users`, `permission_overrides`, `otp_codes`, `user_sessions`, plus the `app_user` DB role and its grants. Tenancy module (`backend/app/modules/tenancy`, migration `0003`): `branches`, `tenant_settings` (`clinics` itself was already covered by Auth — Tenancy just adds update capability and owns the model file now). Patient Management module (`backend/app/modules/patients`, migration `0004`): `patients`, plus the `pg_trgm` extension (fuzzy name search) and two role-permission corrections (see changelog). Doctor Management module (`backend/app/modules/doctors`, migration `0005`): `doctor_profiles`, `user_branch_assignments`, `staff_invites`, plus `users.first_name`/`last_name` (see changelog). Staff Management module (`backend/app/modules/staff`, migration `0006`): `staff_profiles`; no new permission or shared-table changes needed — reuses `staff.manage`, `user_branch_assignments`, and the invite/accept mechanism (relocated to the Auth module's Python code by this migration's accompanying changes — the `staff_invites` table itself is unchanged, see changelog) as-is. Audit Logging (`backend/app/modules/audit`, migration `0007`, fixed by `0009` — see changelog) and a doctor directory read permission (migration `0008`) were added ahead of Phase 2 after an architecture review. Appointments module (`backend/app/modules/appointments`, migration `0010`, **booking only** — online + receptionist booking; walk-in/check-in/queue/vitals/EMR/consultation/e-prescription are separate later modules by explicit scope decision): `appointments`, plus a `role_permissions` correction and a new `appointments.view` permission (see changelog). Check-in module (`backend/app/modules/checkin`, migration `0011`, bundles walk-in registration/check-in/queue-token issuance into one module by explicit decision): `encounters`, `queue_tokens`, plus a `role_permissions` correction and new `checkin.view`/`queue.view` permissions (see changelog). Vitals module (`backend/app/modules/vitals`, migration `0012`): `vitals` (DB-enforced append-only), plus a new `vitals.view` permission. Consultation/E-Prescription module (`backend/app/modules/consultation`, migration `0013`): `consultations`, `prescriptions` (DB-enforced append-only, with-supersession), `prescription_items`, plus a deliberate permission-matrix deviation and new `consultation.view`/`prescription.view` permissions (see changelog). Billing module (`backend/app/modules/billing`, migration `0014`, first migration to actually create `invoices`/`invoice_line_items`/`payments`): a `DRAFT`/`ISSUED`-extended `invoice_status`, an added `NET_BANKING` `payment_method`, plus `invoice_line_items.updated_at` and `payments.notes` gap-fills (see changelog) — no permission changes needed, migration `0001`'s seed already matched the matrix. Financial Reports & Analytics module (`backend/app/modules/reports`, migration `0015`, permission-only — no new tables, pure aggregation over Billing's own data): a new `dashboard.view_own` permission (Doctor, row-scoped), a deliberate matrix deviation (see changelog). Patient EMR Timeline & Medical Documents module (`backend/app/modules/emr`, migration `0016`): `medical_documents` (a purpose-built alternative to the master schema's still-unbuilt polymorphic `documents`, by direct instruction), plus a `patients.view_emr` seed gap fix for `PATIENT` and a new `patients.manage_documents` permission (see changelog). Pharmacy & Inventory Management module (`backend/app/modules/pharmacy`, migration `0017`): `medicines` (with `strength`/`manufacturer`/`reorder_threshold` gap-fills), `medicine_batches`, `pharmacy_inventory_transactions`, plus the `prescription_items.medicine_id` FK migration `0013` deferred and a new `pharmacy.view_catalog` permission (Doctor read access — a seed gap fix; see changelog). Pharmacy OTC / Retail Sales module (same `backend/app/modules/pharmacy` directory, migration `0021`, fulfilling what migration `0017` had deliberately deferred): `pharmacy_sales`/`pharmacy_sale_items` (the sale row is its own receipt — no `invoice_id`/`patient_id`/`branch_id`, a deliberate departure from the master schema's original sketch), a new `pharmacy_sale_status` enum (`PAID`/`REFUNDED`, only `PAID` reachable from the built API), reuses the existing `payment_method` enum for `payment_mode` and `inventory_txn_type`'s existing `SALE` member for stock deduction, plus a new `pharmacy.sell_otc` permission (Receptionist — a deliberate matrix deviation, not a gap fix — see changelog) and the tenant feature gate `features.pharmacy_enabled` (reusing the generic `require_feature_flag()` mechanism Lab introduced). Pathology / Diagnostic Lab Management module (`backend/app/modules/lab`, migration `0018`): a `RESULTED`-instead-of-`PROCESSING` `lab_order_status` (first creation, no `ALTER TYPE` needed), `lab_test_catalog` with `test_code`/`specimen_type`/`turnaround_hours` gap-fills and an array-shaped `reference_ranges`, `lab_orders` with added `patient_id`/`doctor_id`/`resulted_at`/`cancelled_at`/`cancelled_reason`, `lab_results` (unchanged from the master schema), plus a new `lab.view_results` permission (Doctor + Patient — a seed gap fix; see changelog). Every Lab route is additionally gated by a new generic `require_feature_flag()` dependency reading a `TenantSetting` (`features.lab_enabled`), not a schema change. CRM & Follow-ups module (`backend/app/modules/crm`, migration `0019`): `follow_up_status` extended to 5 values (`SENT`/`CONFIRMED`/`OVERDUE` added, first creation, no `ALTER TYPE` needed), `communication_logs` built in its general master-schema shape (`template_id`/`lead_id` with no FK yet — neither `notification_templates` nor `leads` exists), `follow_ups` built deliberately narrower than the master schema's patient-or-lead sketch (`patient_id` required, no `lead_id`), plus `crm.manage` granted to Doctor (a deliberate matrix deviation, not a gap fix — see changelog). `leads` (fulfilled later by migration 0023, see below) and `notification_templates` remained design-only at this point. Clinic Expenses module (`backend/app/modules/expenses`, migration `0020`): `expenses` (a real `expense_category` enum instead of the master schema's free-text `category`, plus a wholly new `expense_payment_mode` enum distinct from the existing patient-payment `payment_method`), plus a new `expenses.record` permission (Receptionist — a deliberate matrix deviation, not a gap fix — see changelog). General (Non-Medicine) Inventory module (`backend/app/modules/inventory`, migration `0022`): `inventory_items`/`inventory_transactions` (design-only since this doc's original draft, never migrated until now), with real `inventory_item_category`/`inventory_unit` enums replacing the sketch's free text, this task's own column names (`current_stock`/`min_reorder_level`), new `cost_per_unit`/`is_active` columns, no `branch_id` (tenant-wide, like `medicines`), and a wholly new `inventory_change_type` enum (`PURCHASE`/`USAGE`/`ADJUSTMENT`/`RETURN`) distinct from Pharmacy's own `inventory_txn_type` — plus two new permissions, `inventory.view` (Doctor, read-only) and `inventory.record_usage` (Receptionist/Nurse/Other Staff, read + `USAGE`-only write — a deliberate matrix deviation, not a gap fix; see changelog). Lead Pipeline / CRM Funnel module (`backend/app/modules/leads`, migration `0023`, finally builds `leads` — design-only since this doc's original draft, deliberately left unbuilt by the CRM & Follow-ups module, migration 0019): real `lead_source`/`lead_status` enums replacing the sketch's free text/`lead_stage` (a genuinely different value set — `APPOINTMENT_SCHEDULED` instead of `QUALIFIED` — so `lead_stage` was removed from the doc rather than reused), `first_name`/`last_name` over the sketch's single `name`, plus a wholly new `lead_interactions` table with no master-schema sketch at all. Two new permissions, `leads.manage` (Owner/Receptionist, full CRUD + convert) and `leads.view` (Doctor, read-only) — deliberately NOT built on the existing `crm.manage` despite the PRD §3 matrix modeling "CRM, leads, follow-ups" as one row, since Doctor already holds `crm.manage` for follow-ups and reusing it here would have silently handed Doctor write access to leads too (see changelog). Notification Templates & Outbox Integration module (`backend/app/modules/notifications`, migration `0024`, finally builds `notification_templates` — design-only since this doc's original draft): reuses the existing `comm_channel` enum for `channel`, keeps `template_key` (renamed from `event_key`) free text by design (an open, non-exhaustive trigger namespace), adds a new JSONB `variables` column. `CommChannel`/`CommStatus`/`CommunicationLog` relocated here from `app.modules.crm.models` (a pure code move — Notifications is now the true owner of the outbox, since every business trigger dispatches through it, not just Follow-ups). `communication_logs` gains a `rendered_body` gap-fill and finally gets its long-deferred `template_id` FK. A shared `dispatch_notification()` function is wired into Appointments' booking, Billing's payment recording, Lab's order completion, and CRM's follow-up creation — each queues a `CommunicationLog` row using an active clinic template if one exists, else a built-in default body. Two new permissions, `notifications.manage` (Owner) and `notifications.view` (Receptionist/Doctor, read-only) — no dedicated PRD §3 matrix row covers this (see changelog). Permission Override write endpoint (`backend/app/modules/auth`, no new migration — `permission_overrides` already existed since migration `0001`, only its write path was missing): `PUT/GET/DELETE /api/v1/permission-overrides`, gated by the existing `staff.manage` (no new permission needed), closing the gap flagged repeatedly across earlier modules' own notes — PRD §13's flagship example (an Owner enabling `vitals.record` for Receptionists at their clinic) is now actually operable, not just resolvable-if-a-row-existed. File Storage & Uploads module (`backend/app/modules/files`, migration `0025`, finally builds `documents` — design-only since this doc's original draft): a small generic file registry (`original_filename` gap-fill added), backed by a swappable `FileStorageBackend` (`app/core/storage.py` — local filesystem implemented, S3/R2 a same-interface swap-in for later), serving three owner kinds (`PATIENT_DOCUMENT`, `LAB_REPORT`, `LETTERHEAD_ASSET`) each dispatched to an existing permission from its own module rather than a new one. Migration `0026` (permission-only, no schema change): grants `prescription.view` to `PATIENT` — a matrix gap the new Prescription PDF feature surfaced (Patient could never call `GET /api/v1/prescriptions/{id}` before this). Migration `0027`: `patients.abha_id`/`patients.abha_address`, two nullable columns for ABHA/ABDM preparedness, deliberately lighter than the PRD's own reserved `AbhaLink` sketch (see that migration's docstring) — writing a non-null value is gated by a new `features.abdm_enabled` TenantSetting (reusing the same generic mechanism Lab/Pharmacy already established, no new column for the flag itself). Three further additions this session needed no migration at all — Prescription PDF generation (`app/modules/consultation/pdf.py`, a new `PRESCRIPTION_PDF` `documents.owner_type`), a channel adapter for notification dispatch (`app/modules/notifications/adapters.py` — `ConsoleChannelAdapter`, the only implementation, resolves `dispatch_notification`'s status to `SENT`/`FAILED` instead of always `QUEUED`), and a payment gateway adapter stub (`app/modules/billing/payment_gateway.py` — `MockPaymentGatewayAdapter`, a new `POST /api/v1/billing/invoices/{id}/create-payment-order` endpoint that creates no `Payment` row). Migrations `0028`/`0029` (permission-only): grant `prescription.view` to `PHARMACY_STAFF` and `pharmacy.view_catalog` to `RECEPTIONIST` — two matrix gaps the Pharmacy Dispense/OTC Sales *frontend* build surfaced, not backend tests (see changelog). Migration `0030`: `invoices.source_type` (reuses `InvoiceLineSource`, no new enum), making Encounter:Invoice genuinely 1-to-N — the duplicate-invoice guard is now scoped to "no second non-VOID invoice of the same source_type" instead of blocking any second invoice outright. A `vitals.record`-for-`RECEPTIONIST` migration was drafted and reverted in the same session, before being applied to any real database — Receptionist's default correctly stays off per the PRD §3 matrix (confirmed by `test_auth_flows.py`'s own PRD §13 flagship-example tests, which assert exactly this default); a clinic that wants Receptionist covering OPD-queue vitals triage grants it per-tenant via the existing `permission_overrides` mechanism (`PUT /api/v1/permission-overrides`), not a blanket role default. **Phase 1 of the Master Handoff phased-development report** (a launch-readiness audit and correction pass, not a new module in §10's build order) added three further migrations. Migration `0031`: `payments` finally joins `vitals`/`prescriptions`/`audit_logs` as DB-enforced append-only (`trg_payments_immutable` + `REVOKE UPDATE, DELETE ... FROM app_user`) — closing an inconsistency this doc's own architecture notes had flagged since migration `0014` ("`payments` is deliberately NOT attached to `prevent_update_delete()`"); no application code changed, since `PaymentRepository` never had an update/delete method to begin with. Migration `0032`: two new read-only permissions, `billing.view` (tenant-wide, alongside the existing `billing.manage`/`billing.view_own`) and `expenses.view` (alongside `expenses.manage`/`expenses.record`) — for a finance/accounts persona, granted via a per-user `permission_overrides` row (`scripts/seed_demo_accounts.py` applies the bundle, plus the pre-existing `dashboard.view`, to its one named demo accounts user) rather than a new ninth role, per the Master Prompt's "do not rebuild the application" rule; zero service-layer scoping changes needed, since `BillingService`/`ExpenseService`/`ReportsService` row-scope by `actor_role` string checks (`DOCTOR`/`PATIENT` only), never by which permission code let the caller through. Migration `0033`: `doctor_profiles.slot_duration_minutes` (`SMALLINT NOT NULL DEFAULT 15`, `CHECK BETWEEN 5 AND 240`) — backs a new per-doctor slot-grid increment on the staff Appointments page (previously a single hardcoded 15-minute frontend constant), read/written through the existing `staff.manage`-gated `PATCH /api/v1/doctors/{user_id}` alongside `working_hours`; no permission change. Also this phase, frontend-only: allergies/chronic-conditions (already-existing `patients.allergies`/`patients.chronic_conditions` columns and API fields since migration `0004`, never rendered anywhere before now) are now editable in the patient registration/edit dialogs and surfaced as a red/amber alert banner on the OPD Consultation Pad and the patient portal's Medical Records page; `pharmacy_auto_replenish_stock` now defaults to `False` (was `True`) so dispensing can never fabricate stock in production by accident. **Phase 2 of the Master Handoff process** ("Patient acquisition & real integrations") added migration `0034`: `appointments.payment_status` (a new `appointment_payment_status` enum — NOT_REQUIRED/PENDING/CONFIRMED/FAILED/REFUNDED — orthogonal to the existing `appointment_status`, which stays the clinical day-of workflow untouched) and a new `payment_gateway_orders` table (its own `payment_gateway_order_status` enum — CREATED/PAID/FAILED/REFUNDED) tracking a public booking's optional online prepayment, deliberately kept separate from `invoices`/`payments` since no clinical encounter exists yet at booking time — see that table's own comment in `docs/schema/clinic_erp_schema.sql`. No permission codes were added this phase (the new public booking/webhook endpoints are unauthenticated by design, not gated by RBAC at all). Everything else here is still design-only, not yet applied to any database. Companion to [`PRD-ARCHITECTURE.md`](./PRD-ARCHITECTURE.md) and the full DDL at [`schema/clinic_erp_schema.sql`](./schema/clinic_erp_schema.sql). Read the SQL file for column-level detail; this doc explains the shape and the handful of decisions made while turning the PRD's entity sketch (§6) into real DDL.

**Tenancy module scope note:** `subscriptions` is deliberately not built yet — PRD §30's pricing-model question is still open, and building the table now would mean guessing at columns that will need to change once billing is actually designed. Clinic *creation* (tenant onboarding) is also out of scope for the Tenancy module as built — it's a Platform Admin operation, and no Platform Admin authentication exists yet (see `platform_admins` in the master schema, still unimplemented). The Tenancy module only manages settings/branches for a clinic that already exists (created today via direct DB access in tests, same as the Auth module's fixtures).

**Patient Management module scope note:** "merge duplicate patients" (PRD §5.1 — a manual, audited action) is not implemented: with no other module yet creating patient-referencing records (appointments, encounters, invoices...), a merge today would just be "delete one of the two rows," which soft-delete already covers. Revisit once a module exists whose records would actually need reassigning between two patient ids. Linking a `patients.user_id` to grant portal access also has no API yet — that's Patient Portal (a later module); the column is set directly in tests the same way other pre-built-module gaps have been handled.

**Doctor Management module scope note:** account provisioning uses a real invite/accept-token flow (`staff_invites`), not an Owner-set password — the invite token is returned in the API response outside `production` (same placeholder-delivery pattern as OTP) since no Communications module exists yet to deliver it by email/SMS. `user_branch_assignments` and `staff_invites` are deliberately generic to any staff role, not doctor-specific, so the Staff Management module reuses both rather than duplicating them. A read-only "doctor directory" for non-Owner/non-Doctor roles (e.g. a Receptionist picking a doctor when booking an appointment) is explicitly out of scope here — the PRD §3 matrix gives every other role "–" for this capability; Appointments (a later module) will need its own, narrower read path.

**Staff Management module scope note:** no self-service "/me" — unlike Doctor Management, the PRD §3 matrix gives no role other than Owner any access to "Staff, roles & permissions," not even "own record," so `employee_code`/`designation`/`joining_date` are Owner-only administrative data (a staff member's own basic identity is already visible via Auth's generic `GET /api/v1/auth/me`). Changing a staff member's `role_code` after creation is also out of scope — it would change their whole permission set, a bigger operation than a profile edit. Reuses `staff.manage`, `user_branch_assignments`, and the invite/accept mechanism as-is; no new permissions were needed.

**Appointments module scope note:** booking only. `Appointment.source = WALK_IN` and `status = CHECKED_IN`/`IN_PROGRESS`/`COMPLETED`/`NO_SHOW` are schema-ready (the full enum was created verbatim) but nothing in this module produces them — walk-in registration, check-in (and the `Encounter` it should create), and queue/token management are separate later modules. Slot availability is derived from the doctor's `working_hours` (from `doctor_profiles`) plus a same-doctor time-overlap check against existing non-cancelled appointments — there is no separately maintained calendar, per PRD §5.1. A doctor with no `working_hours` configured is fail-closed (no day is ever available), not fail-open. `branch_id`/`doctor_id` on the request are validated to exist and (for `doctor_id`) to be an `ACTIVE` doctor; an appointment spanning midnight is rejected rather than mis-validated against day-of-week working hours.

**Changelog:**
- `otp_codes` and `user_sessions` (Identity & RBAC section) were added while implementing the Auth module — not in the original PRD §6 entity sketch. Patient login (PRD §12) needs somewhere to hold a hashed, expiring OTP code, and refresh-token revocation (PRD §12's "opaque, stored server-side... allows revocation") needs somewhere to hold a hashed refresh token per device/session. Both follow the existing event-table convention (created_at only, RLS-scoped, no update trigger).
- Two `role_permissions` seed gaps, both caught by real integration tests failing with unexpected 403s while building the Patient module, corrected in migration `0004`: Lab Staff and Pharmacy Staff were never granted `patients.view_demographics` despite the PRD §3 matrix giving them read access (they need to identify a patient to order a test or dispense a prescription); Owner was granted `patients.view_emr` but not `patients.view_demographics`, which the module's own read endpoints check (Doctor had correctly been granted both in migration `0001` — Owner should have been too). The seed data in this file's own section 17 has been corrected to match.
- `users.first_name`/`last_name` were added in migration `0005` while building Doctor Management — the original schema design (migration `0001`) gave `users` no name field at all, only email/phone, unnoticed until this module needed to show/search a doctor by name. Nullable at the DB level (existing rows and OTP-only patient users may have neither); required at the Pydantic layer for doctor creation specifically. `staff_invites` was added in the same migration for the reason above — no new `role_permissions` gaps were found this time; `staff.manage` (Owner) and `doctor.manage_own_profile` (Doctor) already covered this capability row correctly from migration `0001`.
- The `StaffInvite` Python model, its repository, and the `/accept-invite` endpoint were relocated from the `doctors` module into the Auth module by migration `0006` (Staff Management) — a pure code move, no schema change (the `staff_invites` table itself, created by migration `0005`, is untouched). Activating an invited account is role-agnostic; once Staff Management needed the same mechanism Doctor Management had built, keeping the endpoint at `/api/v1/doctors/accept-invite` would have meant a newly-invited nurse or receptionist posting to a `/doctors/...` URL to activate their own account. It now lives at `/api/v1/auth/accept-invite`, alongside `staff/login` and the other pre-authentication flows.
- Migration `0007` finally built `audit_logs` (PRD §14), flagged since migration `0001` as a Phase 0 deliverable that hadn't actually been created yet. Migration `0008` added `doctors.view_directory` (Receptionist + Patient), a permission not in the original PRD §3 matrix, added ahead of Appointments so booking flows have a read-only, PII-minimal way to list bookable doctors. Migration `0009` fixed a real bug the first append-only table's existence finally exposed: `prevent_update_delete()` (migration `0001`) unconditionally blocked *any* `DELETE`, including the `ON DELETE CASCADE` from `clinics` — harmless in production (nothing deletes a clinic row today) but broke every test whose teardown hard-deletes its throwaway clinic once that clinic had audit-logged activity. Fixed by letting the trigger defer to `app_is_platform_admin()`, the same bypass flag `platform_admin_session()` already sets — application code under `tenant_session` is still unconditionally blocked.
- Migration `0010` (Appointments) found and fixed a third `role_permissions` seed gap (same category as the two fixed in migration `0004`, caught the same way — by this module's own integration tests, not by inspection): Doctor had been granted `appointments.manage` (full create/reschedule/cancel for any patient) since migration `0001`, but the PRD §3 matrix gives Doctor only "R (own)" for this capability. Fixed by revoking that grant and adding `appointments.view` (read, further row-scoped to "own" for Doctor at the service layer — the same scoping pattern already used for `patients.view_emr`), granted to Owner/Doctor/Receptionist/Nurse.
- `docs/schema/clinic_erp_schema.sql`'s own seed data (its section 17) had fallen behind the real migrations for two releases — `doctors.view_directory` (migration `0008`) was missing entirely, and it still had Doctor's incorrect `appointments.manage` grant. Both corrected in the same pass as the `appointments.view` fix above, so the master schema file's seed data matches migration `0010`'s actual end state exactly.
- Migration `0011` (Check-in) added `encounters`/`queue_tokens` and found a fourth `role_permissions` seed gap, same category as the previous three: Nurse had been granted the full `queue.manage` (write) permission since migration `0001`, but the PRD §3 matrix gives Nurse only "R" for both "Walk-in registration & check-in" and "Queue / token management." Fixed by revoking it and adding `checkin.view`/`queue.view` (read, tenant/branch-wide — neither matrix row is marked "(own)" the way Doctor's appointment-booking row is, so unlike Appointments there's no per-doctor row-scoping here), granted to Owner, Doctor, Receptionist, and Nurse.
- Migration `0012` (Vitals) added `vitals` and attached it to the `prevent_update_delete()` append-only trigger already reserved for it since migration `0001` (the first table besides `audit_logs` to actually use that mechanism), plus `REVOKE UPDATE, DELETE ON vitals FROM app_user`. `vitals.record`'s seed (Owner/Doctor/Nurse on, Receptionist off) was already correct from migration `0001` — no gap this time — but there was no read permission at all; added `vitals.view`, granted to Owner/Doctor/Receptionist/Nurse. Patient is deliberately excluded (the "Vitals recording" matrix row gives Patient "–", unlike the broader "Full patient EMR" row's "O read" — patient-facing vitals access is presumed to arrive with the not-yet-built EMR module).
- Migration `0013` (Consultation, Clinical Notes & E-Prescription) added `consultations`, `prescriptions` (append-only, with-supersession per PRD §5.4/§5.7 — same trigger as `vitals`), and `prescription_items` (NOT append-only — `dispensed_quantity` will be mutable once the Pharmacy module dispenses against it). `prescription_items.medicine_id` was created without its `REFERENCES medicines(id)` FK, since `medicines` doesn't exist yet (added by an `ALTER TABLE` once the Pharmacy module creates it); a `route` column was also added, the same kind of sketch-gap `users.first_name` was. **This migration's permission changes are a deliberate product decision by direct instruction, not a seed-vs-matrix gap fix** — the PRD §3 matrix gives Owner only "R" and Nurse "–" for "Consultation, diagnosis, clinical notes" and "E-prescription" (Doctor "F own" only); the product owner explicitly asked for "Doctor/Owner write, Doctor/Owner/Nurse read" instead. `consultation.manage`/`prescription.manage` (already Doctor-only since migration `0001`) were also granted to Owner; new `consultation.view`/`prescription.view` went to Owner, Doctor, and Nurse — Doctor's read is row-scoped to their own `doctor_id` at the service layer, Owner/Nurse reads are tenant-wide.
- `docs/schema/clinic_erp_schema.sql`'s own seed data was resynced again in the same pass as migration `0013`, catching up the `checkin.view`/`queue.view`/`vitals.view`/`consultation.view`/`prescription.view` grants and the Nurse `queue.manage` fix from migrations `0011`-`0013` that had never been back-ported into this file (it had only been kept current through migration `0010`) — same "master schema must match the real end state exactly" discipline as before.
- Migration `0014` (Billing, Invoices & Payments) is the first migration ever to create `invoices`/`invoice_line_items`/`payments` — no earlier migration had touched Billing at all, so unlike every schema deviation before it, there was no `ALTER TYPE`/rename needed to change `invoice_status`: it was simply created as `('DRAFT','ISSUED','PARTIALLY_PAID','PAID','VOID')` from scratch (by direct instruction) instead of the master schema's original `('UNPAID','PARTIALLY_PAID','PAID','VOID')`, with `ISSUED` taking over `UNPAID`'s old meaning and `DRAFT` new — the state in which line items are freely editable. `payment_method` gained `NET_BANKING` (requested), keeping the existing `INSURANCE`/`OTHER` values rather than replacing them. Two schema gap-fills followed the same pattern as `users.first_name`/prescription `route`: `invoice_line_items.updated_at` (in-place editing of a DRAFT line item, not just delete-and-recreate) and `payments.notes` (the master schema's own comment always promised "a row with negative amount + reason" for refunds, but had no column to hold the reason). **No `role_permissions` changes were needed this time** — migration `0001`'s seed for `billing.manage` (Owner/Receptionist), `billing.view_own` (Doctor/Patient), and `payments.record` (Owner/Receptionist) already matched the PRD §3 matrix exactly for both the "Billing & invoices" and "Payments" rows, the first clinical/financial module built so far where that was already true.
- `docs/schema/clinic_erp_schema.sql` was updated directly for migration `0014`'s changes (enum values, the two new columns, `invoice_line_items` added to the `updated_at`-trigger table list) since there was no prior "wrong" seed/DDL to diff against and resync — this is the first time a module's master-schema sync was a direct edit rather than a catch-up correction.

## How it's organized

The SQL file is one linear script, ordered so every `REFERENCES` points at a table already created above it (two exceptions noted inline, fixed up with `ALTER TABLE ... ADD CONSTRAINT` after the fact, to avoid reshuffling the whole file for two forward references). Sections mirror the PRD's domain grouping: tenancy → identity/RBAC → patients/encounters → pharmacy → prescriptions → laboratory → financial → inventory → CRM/communication → audit/documents → reserved-for-later.

## Decisions made while going from PRD sketch to DDL

**Roles and permissions are global, not tenant-scoped.** The PRD's §6 entity sketch mentioned "clinic-scoped custom roles for Other Staff variants" as a maybe. In the actual schema, `roles` and `permissions` are fixed, global reference data (the 8 roles from PRD §2, seeded in the SQL file), and **all** per-clinic customization — including anything an "Other Staff" role might need — goes through `permission_overrides`, which can target either a role or an individual user within one tenant. This is a direct implementation of the two-layer resolution PRD §13 already specified (`role_permissions` defaults → `permission_overrides` deltas); adding tenant-scoped custom roles on top would be a second customization mechanism doing overlapping work. If a clinic genuinely needs a role that doesn't map to any of the 8 (not just a permission tweak), that's a real gap in this design — worth raising if it comes up before implementation.

**Polymorphic references instead of FKs, in four places.** `invoice_line_items.source_type/source_id`, `documents.owner_type/owner_id`, `audit_logs.entity_type/entity_id`, and `pharmacy_inventory_transactions.reference_type/reference_id` all point at "one of several possible tables" and can't be a single real foreign key. Postgres has no native polymorphic FK — these are enforced in the application layer, not the database. This is a real gap the app's service layer must own: nothing stops a bad `owner_type` value or a dangling `owner_id` at the DB level. (`pharmacy_sales.invoice_id` used to be a fifth example here, planned as a deferred `ALTER TABLE` fix-up — migration 0021 built `pharmacy_sales` without any `invoice_id`/`patient_id` column at all, by direct instruction, so this no longer applies; see the changelog.)

**Three tables are genuinely DB-enforced append-only beyond `vitals`.** The product requirement to never overwrite a vitals reading (PRD §5.3) is implemented as a `BEFORE UPDATE OR DELETE` trigger that raises an exception — not just an app-layer convention. The same trigger is applied to `prescriptions` (immutable-with-supersession, PRD §5.7), `audit_logs` (has to be tamper-evident to mean anything, PRD §14), and — as of migration `0031` (Phase 1 of the Clinic ERP / Clinic OS Master Handoff roadmap) — `payments`: a financial ledger is at least as sensitive as a clinical reading, and "insert-mostly by convention" was no longer an acceptable guarantee once this product started handling real money for a commercial launch. A refund is still a new negative-amount row, never an edit — no application code changed, since `PaymentRepository` never had an update/delete method to begin with. Other event-like tables (`pharmacy_inventory_transactions`, `communication_logs`) remain *modeled* as insert-mostly but not DB-locked — a correction there is still a new row with a reason, by convention, not by constraint; revisit if a future compliance review calls for the same hard enforcement there too.

**Row-Level Security is real, not decorative.** Every tenant-owned table has `FORCE ROW LEVEL SECURITY` set, which matters: without `FORCE`, a table's owning role bypasses RLS entirely, and if the application connects as that owning role (common default), RLS silently does nothing. The policies read two session settings the app must set at the start of every request/transaction:

```sql
SET LOCAL app.current_tenant_id = '<tenant-uuid-from-jwt>';
-- only ever set by the Platform Admin service path:
SET LOCAL app.is_platform_admin = 'true';
```

**Recommended (not yet built) DB role setup:** a dedicated `app_user` Postgres role, *not* the table owner, used for all normal request-handling connections — so `FORCE ROW LEVEL SECURITY` actually bites. A separate, more privileged role (or the same role with `app.is_platform_admin` set only from the specific service path that's allowed to use it) for the Platform Admin bypass. Neither role should have `DROP`/`TRUNCATE`, and no role used by application code should have `UPDATE`/`DELETE` on `audit_logs` (belt-and-suspenders alongside the trigger). This is a deployment/ops task for implementation time, not something the DDL alone can guarantee.

**Vitals role is a snapshot, not a live FK.** `vitals.recorded_by_role` stores the role *code as text* at the moment of recording, rather than an FK to `roles`. A role's permissions can change over time (via `permission_overrides`); the historical record of "who recorded this, acting in what capacity, at that moment" should reflect that moment, not whatever the user's role happens to be today. `audit_logs.actor_role` follows the same pattern for the same reason.

**BMI is a generated column.** `vitals.bmi` is `GENERATED ALWAYS AS (...) STORED` from `weight_kg`/`height_cm`, null-safe. One less place for the frontend or backend to get the formula wrong or drift out of sync.

## What's still open

Everything flagged as an open question in [`PRD-ARCHITECTURE.md` §30](./PRD-ARCHITECTURE.md#30-risks-and-architectural-decisions) still applies here — most concretely:
- **Branch model** (assumed: one tenant, many branches) shapes `patients`/`appointments`/`invoices` being branch- vs. tenant-scoped the way they are now. If that assumption is wrong, this schema needs real rework, not a tweak.
- **Subscription/billing model** — `plans`/`subscriptions` are placeholders (seeded with two made-up example plans) pending a real pricing decision.
- **Multi-clinic staff membership** — `users.tenant_id` is `NOT NULL` and singular; a staff member working at two unrelated clinics needs two separate `users` rows today, not one account with two memberships.
